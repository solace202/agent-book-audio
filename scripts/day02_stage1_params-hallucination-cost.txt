这里是第一阶段：LLM 基础与提示词工程。今天是第 2 天，今天的课程是第 2 课：参数、幻觉与成本。

昨天我们讲了模型“看到”什么：token 和上下文窗口。今天讲模型“怎么输出”，以及输出里最让人头疼的两个问题。听完今天这一集，你会知道：温度这个参数到底在调什么；回答为什么会被截断，怎么发现；模型为什么会编造，有哪些办法降低；以及怎么估算一个应用每个月的花费。

先说一个场景。你让模型给一款日本抹茶粉写一句卖点，问了三次，得到三个不同的答案。如果你是做文案的，这挺好，可以挑一挑；但如果你在做客服消息分类，同一条消息三次分到三个类别，那就麻烦了，你连测试都没法写。所以我们得先搞清楚：答案为什么会变。

还记得昨天说的吗？模型每一步要选出下一个 token。具体怎么选呢？它会先给所有候选片段打一个分，再把分数换算成概率，然后按照概率去“抽签”。这个抽签的过程，叫做采样。

温度，英文叫 temperature，调的就是这个概率分布的“尖锐程度”。温度低的时候，概率高度集中在得分最高的那一两个候选上，几乎每次都抽到同一个，输出就稳定、保守。温度高的时候，概率被摊平了，原本排在后面的候选也有机会被抽中，输出就更多样，但也更容易跑偏。

打个比方：温度低，像演员严格照着剧本念台词；温度高，像即兴表演，可能出彩，也可能离题。文字版教程里有一个小互动图，你可以拖动温度，亲眼看到“已发货”“处理中”“已签收”这几个候选的概率怎么变化，晚上记得去玩一下。

那温度该怎么选？一个简单的原则：要稳定的任务，比如分类、信息抽取、输出 JSON，温度设成零或者很低；客服回复草稿，要准确也要语气稳定，可以稍微高一点点；商品标题、营销文案这类需要创意的，可以调高，然后多生成几个候选再挑。

有一点要提醒你：温度设成零，输出通常非常稳定，但不保证每次一字不差。服务端的一些实现细节会带来细微差别。所以做测试的时候，不要用“整段文字完全相等”来判断对错，而是看关键结果，比如分类结果是否一致。

另外你可能还会看到一个参数叫 top p，意思是只在累计概率排在前面的那一部分候选里抽签。一般来说，温度和 top p 调一个就够了，不要两个同时乱调。

第二个话题：截断。每次调用都可以设置一个最大输出长度。模型写到这个上限，就会被强行停下，不管话说没说完。怎么发现呢？接口返回结果里有一个字段，告诉你结束的原因：如果是正常说完，它会标记为 stop；如果是被长度上限截断，就会标记为 length。截断最危险的地方在于输出 JSON 的时候，一个被切掉一半的 JSON，程序是根本解析不了的。所以，凡是要拿去给程序用的输出，都要检查一下结束原因，并且给足长度。

第三个话题，也是今天最重要的：幻觉。

幻觉是指模型一本正经地说出不真实的内容。为什么会这样？回到我们第一天说的本质：模型的目标是生成“看起来合理的下文”，而不是“去查证事实”。当它缺少信息的时候，它依然会补出一个听上去很合理的答案。我常用的比喻是：一个很爱面子的新员工，不懂也不好意思说不懂，于是就编一个。

举个亚米的例子。你问模型：“我们店里编号 YM 九九九九九的抹茶礼盒，保质期多久、产地在哪？”这个商品根本不存在，但模型很可能会给你编出一个“保质期十二个月，产地日本”。如果这是客服在回答顾客，后果可想而知。

怎么降低幻觉？Anthropic 的官方指南里总结了几种做法，我用自己的话讲一遍。第一，明确允许它说“我不知道”或者“资料里没有”。这一条往往立竿见影，因为你给了它一个体面的出口。第二，把依据放进提示词里，并且要求它只能根据给出的资料回答，不许用常识去补。第三，遇到很长的文档，先让它把相关的原句摘出来，再基于这些原句去分析。第四，让它给每一条结论标注出处，事后检查，找不到出处的结论就撤掉。第五，同一个问题多问几次，如果前后答案矛盾，通常说明它在编。

但是一定要记住：这些方法只能降低幻觉，不能消灭幻觉。所以涉及金额、承诺、政策的内容，必须有程序校验或者人工确认。在亚米的场景里，像保质期、成分、过敏原这类问题，正确的做法是让模型只基于商品库里的字段回答，查不到就转人工。后面第二阶段的工具调用、第三阶段的 RAG，就是在解决“把真实资料交给模型”这件事。

最后一个话题：成本和延迟。成本的算法很简单：输入的 token 数乘以输入单价，加上输出的 token 数乘以输出单价。价格通常按每一百万 token 来报。

我们口算一个例子。假设一个客服助手，每次请求输入一千五百个 token，输出两百个 token；输入每百万 token 一美元，输出每百万 token 四美元。那么每次大约是零点零零二三美元，看起来很便宜。但如果每天两万次，一天就是四十六美元，一个月大约一千三百八十美元。所以，小数字乘以大流量，就不是小数字了。

延迟方面也有规律：模型是一个 token 一个 token 生成的，所以输出越长越慢；输入越长，第一个字出来得也越慢。降本提速最直接的办法有三个：少放无关内容、限制输出长度、简单的任务交给更小更便宜的模型。

在回顾之前，我们再聊一个工作中很实际的问题：这三个话题在真实项目里是怎么交织在一起的。假设你要在亚米上线一个“商品问答”小功能，顾客在商品页问：“这个酱油含不含麸质？”你会怎么设置？首先，这是一个事实性问题，答错了可能引发过敏风险，所以温度要设成零，追求稳定。其次，回答不需要很长，最大输出长度设一个合理的上限就行，但要检查结束原因，避免回答说到一半被截断。最关键的是幻觉：你必须把这款商品的成分表放进提示词，明确要求只能根据成分表回答，成分表里没写的，就回答“商品资料中没有相关信息，建议咨询客服”。最后算一下成本：每次带上一份成分表，大概几百个 token，乘以每天的提问量，就能估出每月费用，再和人工客服的成本比一比，你就有了向主管汇报的第一组数字。你看，一个小功能，今天讲的四个知识点全都用上了。

好，回顾一下今天。第一，温度控制采样的随机程度，要稳定就调低，要创意就调高。第二，结束原因是 length 就说明被截断了，JSON 场景要特别小心。第三，幻觉来自模型“补全合理文本”的本性，允许它说不知道、给它资料、要求引用核对，都能降低，但不能消灭。第四，成本等于输入和输出分别计价，再乘以调用量。

今晚打开文字教程，你要完成这几件事：第一，运行参数实验程序，亲眼看看温度为零和温度为一的区别；第二，故意把最大输出长度设得很小，确认结束原因变成了 length；第三，做一次幻觉对比，先不给资料问一个不存在的商品，再给资料并允许它说没有；第四，把价格换成你所用模型的真实价格，算一算月度成本。

三个思考题。第一：如果你的客服分类器在温度为零的情况下，还是偶尔出现不同结果，你会怎么写测试来判断它是否正常？第二：针对“商品保质期查询”，你会在提示词里加哪三条约束来防止编造？第三：你能不能估算一下，你们团队某个想用模型的场景，一个月大概要花多少钱？需要哪几个数字？
