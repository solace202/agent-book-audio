这一课是通往 Agent 的最后一块基础。听完今天，你会知道：怎么让模型稳定地输出程序能用的 JSON，出了错怎么自动修正；什么是提示链，它的好处和代价是什么；还有，服务商提供的原生结构化输出能力，和我们手工的做法是什么关系。

先说为什么需要结构化输出。模型默认说的是给人看的话。可你的系统要做的是：把分类结果写进数据库，根据“是否需要转人工”这个字段决定要不要派单。这就要求输出必须是稳定的、机器可读的结构，最常见的就是 JSON。

问题是，模型输出 JSON 的时候会犯各种小错误。比如在前面加一句“好的，以下是结果”；用 Markdown 的代码块把 JSON 包起来；把布尔值写成中文的“是”；把类别名大小写写错；或者干脆因为长度不够，JSON 只写了一半。每一种都会让你的解析代码崩掉。

怎么办？我把它总结成三层保障，一层不够就叠加下一层。

第一层，提示层。在提示词里写清楚有哪些字段、每个字段是什么类型、允许取哪些值，最好再给一个示例，并且明确要求只输出 JSON，不要任何其他文字。

第二层，解析层。写一个容错的提取函数：去掉代码块的包裹，忽略前后多余的话，把中间那个完整的 JSON 对象取出来。

第三层，校验层。用代码检查：字段齐不齐，类别是不是在允许的范围里，布尔值是不是真正的布尔值。如果不合格，就把具体的错误告诉模型，比如“缺少字段 needs human”，让它修正后重新输出。这叫带错误信息的重试。为什么要告诉它具体错在哪？因为这样它改得更准。还有一个关键：重试必须限制次数，比如最多两次。超过次数还不合格，就走降级方案，比如转人工处理，绝不能无限循环下去。

你会发现，这套思路和你平时处理外部接口很像：不信任输入，先解析，再校验，失败了有重试，重试有上限，最终有兜底。

补充一点，现在很多服务商都提供原生的结构化输出功能，比如 OpenAI 的 Structured Outputs，还有 Claude 的结构化输出功能。你把数据结构的定义交给接口，接口层面就会约束输出必须符合这个结构，可靠性更高。在正式项目里，推荐优先使用这类能力。我们教程手工实现三层保障，一是为了让你理解原理，二是因为各家接口的细节差别很大。另外有个细节要注意：如果你是通过 OpenAI 兼容接口去调用 Claude，严格模式那个参数会被忽略，拿不到结构上的严格保证，要用原生接口才行。不管用不用原生约束，代码里的校验和重试，在生产环境都值得保留。

接下来讲提示链，英文叫 prompt chaining。

意思是把一个大任务拆成几次顺序的模型调用，上一步的输出，作为下一步的输入。打个比方，就像一条流水线，每个工位只做一件事，而且你可以在工位之间检查半成品。Anthropic 在《构建有效的智能体》这篇文章里，把它列为最基础的工作流模式之一。

最常见的一种链条，是自我纠正：先起草，再按照标准审查，最后根据审查意见改写。

我们用亚米客服来演示。顾客发来消息：“订单 A1001 都三天了还没发货！再不发我就投诉了。”我们手上已知的信息是：这个订单状态是待发货，仓库预计明天发出。

第一步，起草。让模型根据已知信息，写一条三句以内的回复。

第二步，审查。另起一次调用，让模型逐条检查这份草稿：有没有已知信息里没有的承诺或者事实？比如草稿里写了“保证明天送到”，这就是一个编出来的承诺，因为我们只知道明天发货，不知道什么时候送到。还要检查语气是否礼貌。没问题就回答“通过”。

第三步，如果审查发现了问题，就根据审查意见改写。

因为每一步都是独立的调用，你可以把每一步的输入输出都记录下来，可以单独评测每一步的效果，甚至可以在某一步插入人工检查。这是一次性写一大段提示词做不到的。

当然，提示链也有代价。每多一步，就多一次调用的延迟和费用。而且错误会沿着链条往下传：如果第一步就编造了内容，后面的步骤可能会把它当成事实。所以每一步都要把原始的已知信息重新带上，审查步骤要对照它来检查。

那什么时候该拆？我的建议是：只有当拆开之后明显更准、或者更可控的时候才拆。能一步做好的，就不要拆。这个判断标准，第四阶段讲智能体设计模式的时候会系统地讲。

最后再聊一个工程上的细节，你作为后端工程师一定会关心：这些逻辑放在哪里？我的建议是，把“调用模型、提取 JSON、校验、重试”封装成一个独立的函数或者服务，对外只暴露一个干净的接口：输入一条消息，返回一个已经校验过的结构化对象，或者返回一个明确的失败状态。调用方完全不需要关心模型偶尔多说了一句话这种细节。同时，把每次的原始输出、重试次数、最终结果都记进日志，这样出了问题可以回放。在亚米的技术栈里，如果分类是异步处理的，比如顾客消息先进入消息队列，再由消费者调用模型，那么最终失败的消息可以进入死信队列，由人工处理。你会发现，大模型应用的很多工程问题，用你已经熟悉的后端手段就能解决。

好，回顾一下今天。第一，要让输出能被程序使用，用三层保障：提示层写清楚格式，解析层容错提取，校验层带错误信息重试，并且限制次数、有兜底。第二，正式项目优先考虑服务商原生的结构化输出能力，但代码校验依然保留。第三，提示链把大任务拆成可检查的步骤，最常见的是起草、审查、改写。第四，提示链会增加延迟和成本，错误也会传递，只在确实值得的时候才拆。

今晚打开文字教程，你要完成这几件事：第一，保存 JSON 工具文件，运行客服消息分析程序；第二，故意把提示词改坏，比如删掉“只输出 JSON”这句话，观察重试机制怎么把输出拉回来；第三，运行起草、审查、改写的提示链，看看审查这一步有没有发现问题；第四，写五条刁难的输入，比如空消息、只有表情、夹带“忽略指令”的消息，看看程序会不会崩。

三个思考题。第一：如果模型连续三次都输出了不合法的 JSON，你的系统应该怎么处理？第二：在起草、审查、改写这个链条里，为什么审查这一步要重新带上已知信息？第三：你们团队有没有哪个现有流程，适合拆成两到三步交给模型来做？
