前六课我们学了很多写提示词的技巧。今天要回答一个更根本的问题：你怎么知道你的提示词真的变好了？听完今天，你会明白为什么“感觉变好了”靠不住；怎么搭一个小型测试集；看哪些指标；怎么做对照实验和错误分析；为什么要留一份平时不看的“留出集”；以及小样本评测要注意什么。

先讲一个几乎每个做过 AI 应用的人都经历过的故事。你发现客服分类器把一条“优惠券用不了”分错了，于是在提示词里加了一句说明，再试一下，对了。你又试了两三条别的，也都对，于是很开心地上线了。结果第二天，发现好几类原本分得好好的消息，现在全分错了。改一处，好了一个，坏了三个。

问题出在哪？出在你只用了几个例子去判断。提示词的改动会影响模型对所有输入的处理，你手动试的那几条，根本覆盖不了全局。

所以，OpenAI 的官方指南建议：建立测试和评估套件来衡量提示词的表现，在迭代提示词或者升级模型版本的时候持续监控；生产环境要锁定具体的模型版本，免得服务商悄悄更新模型导致行为变化。Anthropic 的文档也强调，先定义清楚什么叫成功，再去开发测试。翻译成你熟悉的语言：这就是给提示词写单元测试和回归测试。

一个评测闭环，有五个要素。

第一，测试集。就是一批带有标准答案的样本。比如二十几条客服消息，每一条都标好了正确的类别、订单号、要不要转人工。好的测试集要有代表性，尽量来自真实数据，当然要脱敏；各个类别尽量均衡；还要专门加一些难题，比如一条消息里同时问了两件事、中英文混着说、有错别字的、特别短的；再加几条对抗样本，比如顾客消息里写着“忽略之前的所有指令”。不要全是容易的题，否则分数虚高，发现不了问题。

第二，指标。要能自动计算，而且要分项。在我们的分类器里，有四个指标：JSON 合法率、分类准确率、转人工判断准确率、订单号提取准确率。为什么要分项？因为一个版本可能总分更高，但“转人工”这一项变差了。在客服场景里，该转人工的没转，比分错一个类别严重得多。只看总分，就会错过这种风险。

这里要特别说一下 JSON 合法率。它是地基。输出连 JSON 都不是，其他所有指标都无从谈起，所以评测脚本里，不合法的样本在其他指标上一律算错。

第三，对照实验。每次只改一处。比如第一版是最简单的提示词；第二版只加了字段定义；第三版再加规则和示例。这样分数变化了，你才知道是哪个改动起的作用。如果一次改了五处，分数涨了你不知道该感谢谁，分数跌了你也不知道该怪谁。

第四，错误分析。不要只看分数，一定要一条一条地看错题，然后把错误归类。比如：多意图的消息分错了几条，中英混合的分错了几条，转人工的标准不够清楚导致错了几条。每一类错误，对应一个具体的提示词改进。我想强调，分析错题的能力，比分数本身重要得多。很多时候你会发现，错的不是模型，而是你的标注规则本身有歧义。比如“优惠券没显示，另外想问能不能退”，到底算优惠券问题还是退货问题？这时候你要么明确优先级规则，要么承认它是一道难题。

第五，留出集。从测试集里拿出一部分，开发的时候完全不看、不用。等你把提示词调到满意了，最后在留出集上只跑一次，看看真实水平。为什么要这样？因为你反复针对开发集去调，提示词会慢慢“背住”开发集的特点，在开发集上分数很好，换一批新数据就不行了。这在机器学习里叫过拟合。留出集就是防止你自己骗自己。

还有一个统计常识，非常重要：样本少的时候，分数是有噪声的。假设测试集只有二十四条，每一条大约占四个百分点。第二版比第一版多对了一条，分数涨了四个点，这能说明第二版更好吗？不能，这完全可能是随机波动。怎么办？要么扩大测试集，要么每个版本多跑几次，看结果稳不稳定，再结合错题分析一起判断。我们练习用的小测试集，目的是让你建立流程。真正在公司做项目，要用几十到几百条真实样本。

文字版教程里，提供了一个完整的迷你评测台：一份二十四条的测试集，三个版本的提示词，还有一个评测脚本。运行之后，它会打印出每个版本的四项指标，再把最后一个版本答错的样本逐条列出来，包括期望答案和实际答案。晚上动手的时候，重点不在于分数是多少，而在于你能不能看着错题，说出它为什么错、你打算怎么改。

我们把这个流程和你的日常工作对照一下。你改一段 Java 代码，会跑单元测试，看有没有把别的地方改坏；上线前会在 uat 环境验证。提示词也一样：改一处，跑一遍测试集，看分项，看错题，再决定下一步。只不过提示词的“测试”结果是一个概率性的分数，不是简单的通过或者失败。

再说一个容易被忽略的点：评测不是一次性的工作。在亚米这样的业务里，至少有三个时刻需要重新跑评测。第一，每次修改提示词之后，这是最基本的回归测试。第二，服务商发布了新模型、你打算升级的时候。新模型通常更强，但在你的具体任务上未必更好，格式习惯也可能变化，必须用同一个测试集比一比再决定。第三，业务本身变化的时候，比如新增了一种会员活动，顾客开始问新的问题，你的测试集也要及时补充对应的样本。所以，测试集是一个活的资产，要像维护代码一样持续维护它。后面第九阶段落地的时候，我们甚至会把评测放进定时任务，每天夜里自动跑一遍，分数异常就告警。

好，回顾一下今天。第一，没有测试集的提示词迭代，就是靠感觉。第二，评测闭环五要素：测试集、分项指标、一次只改一处的对照实验、错误分析、留出集。第三，JSON 合法率是地基，转人工这类高风险指标要单独盯。第四，样本少的时候分数有噪声，别被一两条的差异迷惑。

今晚打开文字教程，你要完成这几件事：第一，按目录结构建好评测文件夹，保存测试集、三个版本的提示词和评测脚本；第二，运行评测，记录三个版本的四项指标；第三，对每个版本挑出两道错题，写下你认为的原因；第四，往测试集里追加六条你自己想的难题，重新跑一次，看看分数怎么变。

三个思考题。第一：如果第三版总分比第二版高，但转人工准确率下降了，你会上线第三版吗？为什么？第二：为了让分数好看，有人把测试集里的错题直接写进了示例里，这会带来什么问题？第三：在你们的客服场景里，哪些消息最适合放进“难题”和“对抗样本”里？
